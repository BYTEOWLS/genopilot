# Catalog-first genome sources

## Outcome

After normal setup, a researcher can enter a genome identifier, download its files from the catalog, and inspect them before creating an analysis run. A later workflow can reuse the verified files.

## Scope and contract

- A registered provider must resolve an exact identifier and download the pinned genome. Remote metadata lookup, search by query, and browse without a query are independent optional methods. The catalog offers only the methods implemented; listing saved entries is always available. Each provider declares its downloadable artifacts (supported file kind and label). The review presents that declaration as a checkable list; only selected artifacts are requested. Current supported kinds are FASTA and GFF3.
- The catalog owns identity `(source, id)`, labels, descriptions, and verified cache locations. Each provider validates its own `parameters` mapping and optional metadata. Parameters describe how to request the exact genome; they never contain credentials. Saved workflow inputs snapshot the identity and parameters rather than depending on the current catalog. Breaking changes are expected in this alpha. Do not implement migrations for old catalogs or saved workflow configurations; reject incompatible files without overwriting them.
- NCBI accepts a versioned assembly accession and supports metadata lookup. Use the Datasets REST API from TypeScript; search and browse are not required. Replace the Datasets CLI dependency, not the normal setup flow.
- VEuPathDB owns site selection, release, organism identifier, authentication, and REST requests. Validate parameters against the canonical ID. Verify search support and release coverage before exposing search; never substitute a current release for an unavailable one.
- Catalog downloads and direct Snakemake runs use the same packaged TypeScript download implementation. The resolver retains local inputs and role-specific file requirements. Record provider provenance and checksums; publish only verified files. A failed or cancelled refresh leaves the previous verified copy usable.

### Provider setup

Manage Tools gains an **Accession Providers** tab alongside its existing tooling view. Build the list at runtime by iterating the provider registry. Each row takes its ID, label, short description, fields, and configuration status from the registered definition and its settings. Catalog selectors and downloader dispatch use the same registry; no screen or dispatcher keeps its own provider list. For packaged providers, explicit registration at startup is sufficient: adding a provider changes its module and the registration point, not shared tooling, catalog, or form code. Configuration is separate from runtime setup: a missing provider key must not make the toolchain appear broken.

Providers declare their setup fields, following the declarative approach of `manifest.parameters.yaml`, not its workflow-specific schema. For this release a field needs only `id`, `label`, `kind: secret`, and `required`. Shared code renders the list and masked edit form, validates required fields, and stores secrets by provider and field ID. A provider with no fields needs no form. Site, release, and organism belong to genome selection, not credential setup.

- NCBI declares an optional API key: do not warn in the catalog if absent. Missing required credentials show a warning in the download form and block operations that need remote access until configured. Listing saved entries and inspecting verified local copies remain available. A stored key means **configured**, not verified by the service.
- The download form omits Provider access and optional-key notices. Only missing required credentials show a warning alert and **Configure provider**, opening the matching provider in Manage Tools. The list has no provider-configuration action; notices direct researchers to Manage tooling. Returning restores the catalog selection and rechecks status; never automatically repeat a download.
- Replace the catalog's API-key tab rather than leaving two editors. Use the shared `TabBar`, selectable list, and `EditPage` in `src/ui/tooling-screen/`; use masked shared fields in `src/ui/tooling-screen/provider-form.tsx` and owner-only storage in `src/tooling/provider-settings.ts` (replacing the former NCBI-only key editor/storage). Support set, replace, and explicit clear; never prefill or reveal a stored key. Providers own request authentication, not rendering or storage.

### Implementation handoff (in delivery order)

Treat the steps as the order of work for one full accession refactor, not independently shippable compatibility layers. Refactor or replace the existing accession code and its callers wherever needed. Do not retain old types, UI flows, or adapters just to keep an intermediate step compatible. The finished branch is judged against the release acceptance criteria.

1. **Catalog and provider boundary.** Keep catalog, store, cache discovery, registration, and views together under `src/accessions/`, retaining the locked catalog store. Use one registry; provider-specific implementation belongs under `provider/<id>/` (`ncbi/` now, `veupathdb/` later). Shared operations receive a reference `{source, id, parameters}`; treat loaded parameters as `unknown` until the provider validates them. Extend the reference with `{name?, description?, metadata, cached_copies}` in the catalog. Bump the catalog schema and use the pair for lookup, update, discovery, and deletion. Test two providers with the same ID in `tests/accessions/` before changing the UI.
2. **Provider methods.** `resolveExact` returns a canonical reference; `download` takes that reference, requested file kinds, a staging directory, and an abort signal. It writes files and returns source facts, not catalog mutations. Optional `lookupMetadata`, `search`, and `browse` are detected by method presence. Search and browse return selectable references and display summaries, not downloads. NCBI parameters can be `{}`; a VEuPathDB reference such as `FungiDB-71_AnidulansFGSCA4` carries `{site: FungiDB, release: 71, organism_abbreviation: AnidulansFGSCA4}`. Keep site selection and identifier parsing inside that provider.
3. **NCBI vertical slice.** Use `src/accessions/provider/ncbi/metadata-fetch.ts` for exact lookup. Verify the genome package request and archive members against the [Datasets REST API](https://www.ncbi.nlm.nih.gov/datasets/docs/v2/api/rest-api/). Stream to staging; select only the requested accession's FASTA, requested GFF3, and report. Reject missing or ambiguous matches. Preserve requested `genomic.fna` and/or `genomic.gff`, plus `checksums.json` (one or both of `fasta`, `gff3`, SHA-256) under `<output-root>/<provider-cache-dir>/<id>/`. Preserve `ncbi-accessions-cache` for NCBI. The shared cache writer verifies before replacing; cancellation, disk errors, or concurrent writers must not expose a partial entry. Test with a small synthetic archive and injected HTTP responses.
4. **Catalog action.** Extend `src/ui/accessions-screen/` and reuse `src/accessions/views.ts` for opening verified files. Select the provider, enter the ID (or select a result if supported), and use the default `runs` root without an output-root selector. New-genome selection opens a metadata/reference review before files are downloaded; fetch metadata when lookup is supported, otherwise state that it is unavailable. Lookup failures remain retryable without downloading. The review offers a provider-declared artifact chooser, Save metadata only (no genome files), or explicit Download confirmation. All declared artifacts start checked; Space toggles them. Enter applies the choice; Escape keeps the prior selection. Empty download selections are refused without fetching or saving, while metadata-only saving stays available. Partial refresh preserves verified unchecked artifacts; annotation-only caches are valid but cannot be opened as a genome until FASTA exists. Metadata-only saves preserve existing labels and verified copies; uncached entries remain selectable for on-demand workflow downloads. Show actual transferred bytes, an optional known total, and extraction/verification/publication stages without guessing progress. If requested GFF3 is unavailable, keep any verified FASTA and show that annotation is unavailable; an annotation-only request publishes no empty cache. It remains usable as an annotation-transfer target; only roles requiring GFF3 are blocked. Do not treat a failed GFF3 request as proof that no annotation exists. On success rescan and select the verified entry; on failure retain the record and allow retry. Use provider/field secret storage in `src/tooling/provider-settings.ts`; keep secrets out of parameters, process arguments, URLs, and errors.
5. **Workflow handoff.** In both workflow configuration modules, save the remote reference plus `cache_mode: reuse | refresh`; leave local file inputs alone. When reusing a verified catalog copy outside the run's output root, snapshot its location as well, then recheck the required checksums at resolution. Catalog copies may contain only some artifacts: only snapshot a copy with the role's required files, and never assume FASTA exists. In `scripts/build.mjs` bundle a non-interactive Node entry point under `dist/` that calls the same provider/cache code. `workflows/shared/scripts/resolve_input.py` locates it relative to the packaged script, not the working directory. Pass a nonsecret request (reference, file kinds, root, mode) on stdin; return verified paths, digests, provider facts, and `downloaded` on stdout. Errors go to stderr with a nonzero exit. The Python resolver copies files and writes per-file provenance; verified reuse remains `imported`, `downloaded: false`. Update `resolve_inputs.smk`, `resolve_backbone.smk`, and `collect_run_provenance.py`; remove the Datasets CLI environment, version probes, and citation/tool rows once the REST path passes. Test the packed entry point from an unrelated working directory, not only via the TypeScript dev runner.
6. **VEuPathDB evidence before implementation.** Verify the site-to-host table, authenticated whole-genome file routes, and whether organism lookup/search identifies the requested release. Check one current and one older release with a real key. Record confirmed routes and sanitized response shapes in the provider tests; never store a key or raw genome fixture. If search covers only current releases, label that scope; if unsupported, omit the method. Exercise missing credentials and an unavailable pinned release separately from network failures.
