# Consensus and comparison workflows: design

## Purpose

This document is the design for the workflows that follow `annotation-transfer`: building a reproducible consensus genome from an existing assembly and any number of short-read isolates, transferring a reference annotation onto it, validating the resulting proteins, and comparing the reference and consensus genomes. None of it is implemented yet. Pending work is tracked in [`tasks.md`](../../tasks.md) and deferred ideas in [`later.md`](../../later.md). The contracts established by the first workflow are recorded in [`done/annotation-transfer-workflow.md`](done/annotation-transfer-workflow.md).

Snakemake is the workflow engine. The TUI configures and runs Snakemake, preserves decisions, loads previous results, and presents progress, completion metrics, and result locations. Every workflow must remain runnable without the TUI.

## Core principles

- Keep source data, configuration, decisions, intermediate artifacts, and final results traceable by checksums.
- Use YAML for workflow configuration and saved user decisions.
- Use TSV for sample metadata or result matrices when tabular data is more appropriate.
- Process every isolate independently before aggregating evidence.
- Never silently resolve ambiguous consensus positions or annotation problems.
- Keep imported and cached artifacts visibly distinct from artifacts generated by the current run.
- Pin Snakemake and bioinformatics tool versions through reproducible environments.

## Required inputs

- reference FASTA;
- matching reference GFF3 annotation;
- an existing assembly FASTA, for example a long-read telomere-to-telomere assembly;
- zero or more previously processed compatible artifacts;
- any number of paired-end short-read isolates added through saved isolate metadata.

Basecalling and de novo assembly are outside scope. The reference FASTA/GFF3 and the assembly FASTA may each be supplied as a local path or as a versioned NCBI assembly accession, as in `annotation-transfer`.

## Candidate toolchain

- LiftOn for annotation transfer, using its Liftoff DNA-alignment and miniprot protein-alignment dependencies;
- gffread for CDS and protein extraction;
- BUSCO for separate genome- and protein-level completeness checks;
- minimap2 with an assembly preset and/or MUMmer for assembly comparison;
- QUAST for assembly statistics;
- BLASTP only as secondary evidence for unmatched or problematic proteins;
- NCBI Datasets CLI (`ncbi-datasets-cli`) to resolve an accession-sourced reference or target input into local FASTA/GFF3 files.

Potential later annotation evidence tools such as BRAKER belong in [`later.md`](../../later.md). Miniprot is part of the pinned LiftOn runtime rather than a separate annotation stage. Select the short-read QC, mapper, variant caller, consensus method, repeat/transposon tools, and antiSMASH setup independently on their merits.

## Saved isolate catalog

The TUI must allow isolates to be added one at a time and reused across runs. Each isolate has a stable name, input path or explicit paired-read paths, an optional description, and optional lineage information.

```yaml
isolates:
  - id: isolate-a
    path: /data/illumina/isolate-a
    description: Wild-type isolate

  - id: isolate-b
    path: /data/illumina/isolate-b
    description: Derived strain
    derived_from: isolate-a
```

The importer validates that names are unique and resolves a directory into explicit read files before execution. The saved configuration must remain extensible when another isolate becomes available.

All configured isolates are aligned, called, and reported. Excluding an isolate from consensus voting never removes its analysis results.

## Workflow stages

### 1. Baseline annotation transfer

Run LiftOn reproducibly inside Snakemake:

```text
reference FASTA + reference GFF3 + initial assembly FASTA
    -> LiftOn
    -> configurable annotation-ID prefixing
    -> GFF3 validation
    -> CDS and protein extraction
    -> protein validation
```

LiftOn combines Liftoff DNA-based transfer with miniprot protein evidence and can report rescued, duplicated, and unmapped features. Its output identifiers are not assumed to satisfy the configurable prefixing required here. Prefixing is therefore a deterministic post-processing step, and the raw LiftOn GFF3 is preserved separately.

The prefix is configurable, for example `XY_`, and is applied consistently to feature IDs and references such as `Parent` without blindly replacing text in descriptions. Validate GFF3 hierarchy and uniqueness afterwards.

GFF3 feature IDs must be valid within the annotation file. For NCBI submission, also verify the separate NCBI locus-tag-prefix requirements: an official locus-tag prefix is assigned or accepted by NCBI and must not collide with another submitter's prefix.

Protein validation initially reports:

- premature or internal stop codons;
- missing start or stop codons;
- CDS lengths not divisible by three;
- frameshifts and changed protein lengths;
- amino-acid substitutions;
- mapped, unmapped, and duplicated coding features.

### 2. Per-isolate processing

For every configured isolate:

```text
paired FASTQ
    -> input validation and QC
    -> alignment to the initial assembly
    -> sorted/indexed BAM
    -> mapping and coverage metrics
    -> callable positions and variant calls
```

The implementation supports any number of isolates and does not encode any sample name in workflow rules.

### 3. Consensus assessment

The initial assembly's base contributes one vote in addition to all callable isolate votes.

```text
per-isolate calls + assembly vote
    -> per-position support matrix
    -> IUPAC diagnostic consensus
    -> tie and ambiguity report
```

No-call and filtered positions do not count as isolate votes. Coverage and genotype-quality thresholds must be explicit configuration values.

The diagnostic outputs include the IUPAC FASTA, ambiguity counts by code, affected coding regions where available, and the underlying per-isolate support for every ambiguous SNP. Tied indels are reported separately because IUPAC codes cannot represent insertions or deletions.

### 4. User decision and consensus rerun

The TUI presents the number and types of tied positions and the list of participating isolates. It allows the user to rerun consensus aggregation after excluding any selected isolate or isolates from voting.

For example, a researcher may exclude `isolate-b` because it is derived from `isolate-a`, which already votes. The lineage is data entered in the isolate metadata, never a hard-coded workflow rule.

The decision is saved before rerunning:

```yaml
consensus_decision:
  include_assembly_vote: true
  excluded_from_voting:
    - isolate-b
  reason: Recalculated after reviewing tied-position counts.
```

Read QC, alignment, and variant calling are reused. Only consensus aggregation and dependent downstream rules rerun.

If ties remain, the TUI asks for and records the chosen resolution policy or explicit site decisions. The diagnostic consensus retains IUPAC codes, while the final publication consensus must contain one concrete base at every position. Indel decisions are handled explicitly and retained with the same provenance.

### 5. Final annotation transfer

Only the resolved publication consensus enters final annotation and downstream analyses:

```text
reference FASTA + reference GFF3 + final consensus FASTA
    -> LiftOn
    -> same configured ID-prefix transformation
    -> GFF3 validation
    -> CDS and protein extraction
    -> protein validation
```

Semantic comparison of the baseline and final LiftOn GFF3 files is deferred until it is needed; both source files and their run provenance are retained.

### 6. Required comparisons

After the final consensus exists, run:

1. a per-isolate SNP/indel and shared-versus-specific variation summary;
2. a reference-versus-consensus whole-genome alignment and basic structural summary;
3. a transposon/repeat comparison using the same tool, parameters, and repeat library for both genomes;
4. an antiSMASH analysis using the same tool and database versions for the reference and consensus genomes.

Keep the initial comparisons focused. More advanced gene-model, structural-variant, and manual correction questions are deferred to [`later.md`](../../later.md).

## Loading, continuing, and rerunning

Loading processed data is a core feature, not an optional convenience. A researcher must be able to open a previous run, continue from any supported pipeline stage, rerun a selected stage, and regenerate downstream reports or visualizations without repeating expensive upstream computation.

### Run workspace

Every run has a self-describing workspace:

```text
runs/<run-id>/
├── config.yaml
├── isolates.yaml
├── decisions.yaml
├── artifacts.yaml
├── events.jsonl
├── logs/
└── results/
```

`artifacts.yaml` records each reusable artifact's stage, path, checksum, producing workflow/tool version, relevant configuration checksum, and whether it was generated, imported, or cached.

### Supported run modes

The TUI provides:

- **new run**: start from raw inputs;
- **resume run**: continue an interrupted or incomplete Snakemake run;
- **continue from stage**: load compatible processed artifacts and calculate only missing downstream outputs;
- **rerun stage**: force a selected rule or stage and all affected downstream outputs;
- **visualization/presentation run**: load a prepared artifact set and run only lightweight summaries, reports, plots, or review screens.

Use Snakemake's dependency graph, targets, incomplete-run handling, and forced-rule execution instead of implementing a second scheduler in TypeScript. Imported artifacts must satisfy the same format and compatibility validation as generated outputs. Never manipulate timestamps merely to trick Snakemake into accepting an artifact.

A presentation run must clearly label cached or imported stages. It must not simulate expensive work. It demonstrates real transformations from stored artifacts into reports, visualizations, or review decisions.

### Interactive boundaries

Snakemake rules remain non-interactive. The TUI executes a workflow target up to an explicit decision boundary, displays the generated report, saves the user's decision to YAML, and starts the next target. Direct Snakemake users can make the same decision by editing the documented YAML file.

## TUI minimum scope

The usability goal is that a researcher installs Node, starts the CLI, and is guided through provisioning the remaining workflow runtime. Node alone cannot execute Snakemake, LiftOn, BUSCO, or the other bioinformatics tools. The TUI must therefore verify or bootstrap a pinned Pixi runtime, with user consent and verified downloads. Pixi installs pinned Snakemake and Conda packages together, and Snakemake uses Conda to provision pinned per-rule environments. A container-based alternative may be added later.

The initial TUI provides:

- workflow selection by stable ID, presenting each workflow's label and detailed description, plus run selection;
- isolate creation, editing, reuse, and lineage metadata;
- YAML configuration loading and saving;
- input and artifact compatibility checks;
- guided Pixi, Snakemake, and Conda bootstrap/checks without requiring users to install every bioinformatics tool manually;
- dry-run preview and the exact underlying command;
- structured progress, running/completed/failed jobs, recent messages, and full log locations;
- consensus ambiguity review and saved isolate-exclusion decisions;
- resume, continue, rerun, and presentation modes;
- clear result and provenance locations;
- completion summaries containing duration, workflow metrics, and produced artifacts;
- cancellation propagated to Snakemake.

Core result summaries are presented in the TUI and retained as machine-readable JSON or TSV artifacts. Browser-based HTML reports and React/Chart.js visualizations are deferred to [`later.md`](../../later.md).

Structured JSONL events come from the packaged Snakemake logger plugin. Capture complete stdout and stderr separately from the rendered dashboard.

## Implementation order

[`tasks.md`](../../tasks.md) is the authoritative tracker. The broader order is:

1. Done: the `annotation-transfer` workflow with its generic contracts, direct-Snakemake execution, TUI integration, and basic resume support.
2. Extend the reusable annotation pipeline with CDS/protein extraction and protein validation.
3. Define isolate metadata contracts and implement per-isolate QC, alignment, coverage, and variant calling.
4. Define consensus-decision contracts and implement support aggregation, IUPAC diagnostics, saved decisions, and final consensus generation.
5. Run LiftOn and protein validation on the final consensus.
6. Implement continue-from-stage, rerun-stage, and presentation modes using validated synthetic and prepared artifacts.
7. Implement basic isolate and reference-versus-consensus comparisons.
8. Add required repeat/transposon and antiSMASH analyses.
9. Add deferred features only when their inputs and scientific requirements are available.

## Testing and acceptance

Use small synthetic FASTA, FASTQ, GFF3, BAM/VCF, and processed-artifact fixtures. Tests must cover:

- direct Snakemake execution without the TUI;
- unique stable workflow IDs and loading an existing run after its workflow label changes;
- visible workflow descriptions during TUI selection;
- any number of isolates and reusable isolate metadata;
- assembly voting and tied SNP/indel reporting;
- generic isolate exclusion and saved decisions;
- deterministic prefix transformation and GFF3 ID validation;
- protein validation fixtures with known stop and frame problems;
- interruption and resume;
- loading valid and incompatible processed artifacts;
- rerunning one stage and the correct downstream dependency set;
- visualization-only presentation runs;
- equivalent outputs from fresh and correctly resumed runs;
- TUI success, failure, cancellation, and complete log retention.
