# Changelog

All notable changes are documented here. Versions follow Semantic Versioning and remain in the `0.x.x` range while the CLI and workflow contracts are under active development.

## [Unreleased]

### Added

- `genopilot` command (short alias `gnp`) with an Ink welcome screen showing package metadata, tooling status, keyboard command selection, responsive layout, and double-`Ctrl+C` exit confirmation.
- Text fields with Backspace and Delete on either side of the cursor, Home/End and Ctrl+A/Ctrl+E (Cmd+←/→ where the terminal sends them) for the line start and end, and Option+←/→ and Option+Backspace for words; Backspace at the start of a field no longer deletes the text after the cursor.
- `h` returns to the home screen from any nested screen; it is typed into a focused text field and unavailable while a run, deletion, or save is in progress.
- Terminal window title set from the package label, extended with the selected workflow's label, a ⏳ mark while Snakemake runs, a ✔ or ✖ outcome mark once it finishes, and restored on exit.
- Process title set to the command name, so `ps` lists `genopilot` instead of the `node` invocation.
- Consent-based, user-local tooling setup under a managed `~/.byteowlsGenopilot` directory (XDG data path on Linux): verified Pixi downloads, pinned Snakemake and Conda, version validation against supported ranges, per-tool availability markers, streamed installation progress, cancellation, and retryable checks.
- Background update notice and `genopilot update`, a non-interactive self-update that installs the exact newer npm release.
- **Manage isolates** command with a user-local, versioned isolate catalog: create, edit, and remove isolates with a suggested stable ID, optional wild-type (yes, no, or not recorded) and `derived_from` lineage metadata, and one or more R1/R2 FASTQ pairs (one per lane or run), each typed (including `~` paths) or chosen from a file browser that opens beside the pair's other mate, and flagged when already trimmed by the provider; lightweight plain/gzip FASTQ checks; rejection of duplicate IDs, a read path used twice anywhere in the catalog or one file reached twice through links within an isolate, missing parents, and lineage cycles; removal refused while other isolates derive from the isolate; and locked, atomic saves that detect edits from another window and never overwrite a corrupt catalog.
- Import isolates from an Illumina sequencing delivery folder: a read-only scan groups FASTQ pairs by sample into read sets (per lane and run, lane-merged files included) and copies of the same reads, samples at most about 1,000 records per file with bounded memory, reports every file it does not propose with its reason (index reads, split chunks, undetermined reads, missing or mismatched mates, invalid FASTQ, links leaving the folder, files already in the catalog), and suggests raw or trimmed reads from read lengths; a review lets the researcher create new isolates or add read sets to existing ones, pick one copy per read set, and confirm each trimmed flag, with a help page (`?`) that explains every review row, and all accepted isolates are saved in one catalog update that keeps review decisions when another window changed the catalog. Delivered files are never modified.
- **Manage NCBI accessions** command, organized in tabs, with a user-local, versioned accession catalog: label versioned assembly accessions with a local name and description, look up and refresh lightweight NCBI metadata (organism, taxon, assembly name, level, status, and strain when reported) with its retrieval provenance through the NCBI Datasets v2 API, and save offline without metadata; offline discovery of verified workflow caches under `./runs` and researcher-managed output roots, with damaged caches explained but never trusted and conflicting copies flagged; removal deletes the accession's cached files after confirmation. A successful run that used an NCBI input records its cache automatically.
- One page layout across screens: a bold, underlined title, an optional description, and a shortcut line that always ends with Esc and `h — Home`; forms, including the workflow configuration, save with a `[ … ]` button instead of Enter on any field, and local file paths are typed or pasted or browsed with Enter from one field.
- Optional NCBI API key, entered, replaced, and cleared in its own tab, stored in a private user-local file, never rendered in full, sent only as a request header for metadata lookups, and passed to runs only through the child-process environment.
- New-run flow with packaged workflow discovery by stable ID and a manifest-driven configuration form: sections, required markers, defaults, placeholders, previews, conditional fields, typed or browsed file paths, radio choices, validation, and confirmation.
- Prefill the form from previous runs with PageUp/PageDown (or `fn` + ↑/↓), listing each run by its name and creation time.
- Packaged `annotation-transfer` workflow with strict, versioned manifest and configuration contracts, a pinned LiftOn 1.0.13 same-species profile, requested and effective CPU selection, an optional annotation ID prefix, and declared presentation stages and result artifacts. LiftOn starts only after the input FASTA and GFF3 files passed validation; a failed validation stops the run and keeps its report.
- Reference (FASTA + GFF3) and target (FASTA) inputs that each come from a local path or a versioned NCBI assembly accession, with detection of existing accession caches and an explicit, saved choice to reuse or refresh them. Accessions are typed or pasted (case and surrounding whitespace are ignored), checked as you type against the versioned format and the accession catalog, or chosen from the catalog with Enter. An accession whose cataloged copies have conflicting checksums is explained, listed with its copies, and refused.
- Run directories named by a validated `run.id` (UTC timestamp plus a filesystem-safe run name), with the run name, description, and `run.created_at` recorded in `config.yaml`.
- Start a saved run as a dry run or a real execution, chosen independently, with the exact managed Snakemake command shown before starting and timestamped stdout/stderr logs kept for every attempt.
- Execution screen with a terminal-sized, scrollable live log (arrow keys, PageUp/PageDown, `g`, `G`) and per-stage progress read from a versioned `events.jsonl`, which a packaged Snakemake logger plugin also writes when the workflow runs without the TUI.
- Snakemake per-rule Conda environments shared across runs through a managed `conda-envs` directory, while each run keeps its own job metadata and locks.
- Run-results screen for annotation-transfer runs in tabs like the reference-consensus results: an overview of the execution outcome, the status, and the final GFF3 validation; the transfer metrics labelled by their counting unit; the model evidence; the files, with missing-artifact warnings, direct report and evidence paths, provenance, and complete-log locations; and the run details. A finished execution stays on screen until results are requested.
- Result help page (`?`) showing the workflow's results documentation, which explains every result item and each LiftOn transfer method and mutation class, next to the run metadata and files every workflow shares.
- Packaged `reference-consensus` workflow configuration: one backbone from a local FASTA, a typed or cataloged versioned NCBI accession, or the file browser; one or more isolates chosen from the isolate catalog in a searchable multi-select, with the count derived from the selection; strict-majority (default) or plurality voting; an optional backbone vote; a minimum of callable isolates (default 0, at most the number selected); `N` (default) or IUPAC codes for unresolved SNPs; editable haploid calling thresholds (minimum depth, mapping quality, base quality, and allele fraction); and the established CPU and run-detail fields. Saving creates the run directory with `config.yaml` and an immutable `isolates.yaml` snapshot of the selected catalog records, written together or not at all.
- Consensus review with the backbone's identity, cache decision, and known checksum, every isolate with its read files, trimmed and wild-type status and lineage, a voting explanation with worked examples, all effective parameters, and the run directory; the exact Snakemake command is shown on the start page. Missing or unreadable read files block the run; linked duplicate read files, an isolate that may be the backbone's own sample, and mixed trimmed and untrimmed reads are shown as warnings. A review taller than the terminal scrolls.
- The consensus Snakefile resolves the backbone and validates the backbone FASTA and every snapshot read file, and runs directly through Snakemake with a configuration the application saved.
- Per-isolate consensus processing, executable from the TUI and directly through Snakemake: every read pair's read group is derived from its Illumina read names (a pair without them fails with a clear message) and its files are checksummed; fastp 1.3.7 trims adapters; BWA 0.7.19 aligns to the backbone; duplicates are marked per library across all runs of that library with samtools 1.24; BCFtools 1.24 calls every covered position haploid with the run's thresholds. Each isolate gets its BAM, alignment and coverage metrics, an indexed all-sites BCF, a callable mask that tells callable, ambiguous, and uncallable bases apart, normalized variants with named filters, a reference-guided FASTA of `A/C/G/T/N` with a chain file, metrics, provenance, and a promotion candidate for the isolate catalog. Isolates run in parallel within the run's CPUs; the run records every artifact's checksum, the tool versions, and the commands.
- Cohort support aggregation: once every selected isolate is processed, the backbone's optional vote and one vote from every isolate callable at a position are counted into indexed, versioned support tables. Overlapping variants of different isolates form one locus in which every voter chooses one complete allele. Ambiguous and uncallable isolates cast no vote, and loci are flagged as SNP, indel, multiallelic, overlapping, competing indel, or unsupported. A summary adds vote and callability histograms and an allele frequency spectrum. Changing only the backbone vote reruns aggregation alone.
- Cohort consensus generation: the configured voting method picks the winning allele at every locus of the support table, and the backbone base elsewhere. Ties, missing majorities, positions without votes, and positions below the minimum of callable isolates are never guessed: they are written as `N`, or an unresolved SNP as the IUPAC code of its voted alleles when chosen, and an unresolved indel as `N` over its backbone span. An indexed consensus sites table records every locus's decision, reason, written sequence, and backbone and consensus coordinates, and every unresolved region; a summary adds the policies, input checksums, and counts per decision, reason, flag, and representation. The consensus FASTA keeps the backbone's sequence names and order. Changing only a consensus setting reruns consensus generation alone.
- Cohort iterations: a saved, reasoned decision (`decisions/iteration-<n>.yaml`) changes the voting isolates and any of the four cohort settings and reruns only support aggregation and consensus generation into `results/cohort/iteration-<n>/`, directly through Snakemake with `provenance/cohort/iteration-<n>.json` as the target. The first cohort and earlier iterations stay unchanged, and no isolate is aligned or called again. An isolate that failed can be excluded this way, which completes the run from the other isolates' results and records the failed isolate as excluded and incomplete. The application validates decisions against the run and saves them without ever replacing one. The cohort rules' outputs are now patterns, so runs created before this change regenerate their first cohort on their next attempt.
- Results of reference-consensus runs, after execution and from **Open existing run**, in tabs: an overview of the backbone, the active cohort's voting settings and voters, and its selected and unresolved loci by reason; every isolate with its snapshot lineage metadata, processing state, depth, callable share, variant counts, vote, and promotion candidate, with the paths to its alignment, variants, masks, FASTA, records, and logs; every cohort iteration with its state, reason, settings, files, and a comparison of its counts with the first completed cohort; the run records; and the run details. States are read from the records the workflow wrote: an isolate without a promotion candidate is incomplete, a decision without provenance is pending, and a decision changed after its iteration ran makes that iteration invalid. One unreadable record is reported without hiding the rest, and the help page explains every item and the scientific terms from the workflow's `results.md`.
- Cohort review and rerun from the reference-consensus results: a **Sites** tab lists the ties, loci without a majority, competing indels, or every unresolved locus of the iteration selected on the Iterations tab, with the backbone's vote and every voter's allele or callability state and lineage metadata; a review form (`r`) chooses the voting isolates, also excluding one whose processing failed, and the four cohort settings, and saves them with a required reason as the next iteration. The rerun dry-runs `provenance/cohort/iteration-<n>.json` and executes it only when the dry run's structured events list nothing but the three cohort rules; otherwise it names the other rules and explains that the change needs a new run, keeping the decision as a pending iteration. A pending or interrupted iteration is continued (`c`) the same way. Iteration logs are kept under `logs/cohort/iteration-<n>/`, and the results reload afterwards with the new iteration selected.
- An execution's progress now starts where the run's `events.jsonl` ended, so an earlier attempt's events are no longer shown again.
- Runs start Snakemake with `--keep-going`, so one failing isolate is reported as failed while the others finish.
- The execution screen shows each isolate with a progress bar, its finished and expected steps, and its current step or outcome; isolates finished in an earlier attempt show as done, also when the run fails again; in a short terminal, failing and running isolates stay visible. Run events now carry each job's wildcards, outputs, and command.
- **Open existing run** command listing runs in the default `runs` collection with compatibility and status checks, opening their persisted results without starting Snakemake, and permanently deleting a run only after explicit confirmation.
- Documentation in Markdown that GitHub and the application render alike: general pages in `docs/`, and per workflow a `README.md` on its science, inputs, parameters, steps, outputs, and tools and a `results.md` on its result page. **Help** on the welcome screen opens a documentation index built from the discovered workflows, with each topic's documents as tabs; the workflow selection opens the highlighted workflow's README with `?`.
- Built-in renderer for the documentation's Markdown subset (headings, paragraphs, lists, tables, code blocks, GitHub alerts, inline code, bold, italic, and links) with colours and cues that keep it readable without colour, and no added dependency.
- Mouse-wheel and trackpad scrolling everywhere ↑/↓ scroll or select, in any terminal that reports the mouse; text is selected with a modifier key while dragging (Shift in most terminals, Option in iTerm2). Choices in the run configuration and the NCBI cache decision now change with Space or ←/→, as in every other form, so scrolling never changes a value.
